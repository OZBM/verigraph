VeriGraph is a programming system built for AI. Every piece of a program states a promise: what it needs, and what it guarantees. A solver checks each promise for every possible input before the program is built. When a promise can break, the AI gets the exact input that breaks it, and fixes the code.

The problem, and the idea
The problem

AI writes code faster than anyone can check it.

The usual safety net is testing: run the code on some inputs and see whether the answers look right. But a piece of code that takes just two ordinary numbers (32 bits each) has about 18 billion billion possible inputs (264). Even a large collection of tests tries a tiny fraction. A bug can hide in any of the rest.

Testingsamples a few inputs

Each blue dot is one tested input: all passed. The red one was never tried, and it breaks the program.

Provingcovers every input

The solver reasons about all inputs at once. If any input breaks the promise, it returns that exact input.

The idea

Give every piece of code a promise. Check the promise with math.

1Promise

Each piece says what it needs and what it guarantees. “Give me any finite number; I return one between −1 and 1, with the same sign.”

2Proof

A solver, software that reasons about logic like a tireless mathematician, checks the promise for all inputs at once, not one at a time.

3Repair

If the promise can break, the solver returns the exact input that breaks it. The AI fixes the code and asks again, until every promise is proven.

</> For expertsContract clauses (PRE, POST, INVARIANT, DECREASES, COST) produce proof obligations. Each obligation is one quantifier-free SMT query over bit-vectors, IEEE floats, arrays and uninterpreted functions; bounded forall is discharged by fresh-element rules. UNSAT means proven. SAT yields a model that is replayed in the reference interpreter before it is reported as a counterexample. UNKNOWN or a timeout never counts as a proof.

Testing is a spot check. A proof inspects every beam of the building, and points to the weak one.

How it works
How it works

From a sentence to a proven program.

A VeriGraph program is not a text file but a graph: small pieces connected by wires that carry data. Each piece states its promise and gets a fingerprint computed from its own content. Here is the path from your request to running software.

Words you will see
PromiseThe contract of a piece: what it needs (precondition) and what it guarantees (postcondition).
SolverSoftware that decides whether a logical statement can ever be false. VeriGraph uses three: z3, cvc5, bitwuzla.
CounterexampleA concrete input that breaks a promise, replayed to confirm it really does.
FingerprintAn ID computed from the content itself: same content, same ID, on every machine.
GraphThe program drawn as pieces (nodes) joined by wires (data). So an AI can write, check and repair it piece by piece.
</> For experts · the three gatesGate 1 parses VG-Sym, canonicalizes each node and Merkle-hashes it with BLAKE3 in derive-key mode; mutually recursive nodes are hashed together. Gate 2 infers types one op at a time, checks effects as a capability set and orders side effects with Eff tokens. Gate 3 runs a seeded concrete pre-screen in the interpreter, rejects vacuous contracts, then sends one SMT query per obligation, cached under the hash of its canonical SMT-LIB2 text.

A worked example
A worked example

The input no test would try.

The first milestone is an audio limiter that keeps every sound sample between −1 and 1. Real audio stays near that range, but the promise says any finite number, so the checker must find the huge input that breaks the AI’s first draft.

1The promise, in plain English

The toolchain renders the formal contract in English by fixed rules, so you confirm what will actually be proven:

Requires: x is finite, and knee ≥ 0.5, and knee ≤ 0.99 (the f32 value 0.9900000095367431640625). Ensures: the result ≥ −1.0, and the result ≤ 1.0, and (x ≥ 0.0) is true exactly when (the result ≥ 0.0) is true.

2The AI’s first draft

To squeeze loud samples smoothly, it computes t ÷ (1 + t), where t measures how far the sample goes past the knee (the level where squeezing starts). For any sound you will ever hear, that works.

%4 = FDIV(%2, %3); // t: overflows for huge x %5 = FADD(1.0:f32, %4); %6 = FDIV(%4, %5); // BUG: inf / inf is NaN

3The checker’s answer

A counterexample: x = 3.0 × 1038, knee = 0.5, with the few steps that matter:

%4t, the excess past the knee∞
%51 + t∞
%6∞ ÷ ∞NaN
%12final step: force into [−1, 1]NaN, fails

NaN (“not a number”) fails every comparison, so “the result ≥ −1.0” is false: the promise breaks.

4The repair

Compute 1 − 1 ÷ (1 + t) instead: on paper the same curve, but when t is infinite, 1 ÷ ∞ is 0, so the answer is exactly 1.

%6 = FDIV(1.0:f32, %5); %7 = FSUB(1.0:f32, %6); // u = 1 - 1/(1+t)
Next, the checker must prove the repair for every input. The specification records a float32 simulation over 400,000 inputs, extremes included, with no violation, but a simulation is not a proof. Milestone M1 (expected 4 December 2026) must reproduce this whole story with the real toolchain.
</> For expertsWhy the sign clause: a clamp that mapped NaN to −1.0 would pass the range check while flipping loud positive samples negative. Range checks alone let wrong answers through; relational facts catch them. The frame’s COST clause (heap_bytes == 0 && arena_bytes == 0) is proven; its 500 µs latency BUDGET is measured, never claimed as proven.

Why it matters
Why it matters

Eight advantages, in plain words.

Each card says what it means for you, then what makes it true.

Proven, not sampled

Every promise is checked for every possible input, not for a handful of test cases.

</>One quantifier-free SMT query per obligation; bounded forall via fresh-element rules; UNKNOWN is never a proof.

Every bug comes with its cause

A failure arrives with the exact input that triggers it and the few steps that matter, so the AI knows what to fix.

</>Models replayed in vg-interp; verdicts counterexample, contract_gap, vacuous, unknown. G6 target: failing slices of 5 ops or fewer on 80% of seeded bugs.

Works with any AI

Claude, Gemini, GPT or any other model that can use tools writes VeriGraph through one standard interface.

</>vg mcp, a stdio MCP server with 8 tools; typed JSON diagnostics with stable codes; define-before-use text, so every prefix can be checked.

You confirm what gets proven

The promise is read back to you in plain English, so you can catch a perfect proof of the wrong idea before it ships.

</>contract_text renders contracts from fixed templates, not from the agent’s summary. Intent validation with solver-chosen examples is research track R-14.

Prove once, reuse everywhere

Each piece is identified by its content, so a proof done once holds for everyone who uses that exact piece.

</>BLAKE3 derive-key hash of the canonical graph and contract; proofs cached under the hash of canonical SMT-LIB2 text; same input, same bytes.

Find code by what it does

Search a library of proven parts by the promise you need, not by a package name you have to guess.

</>VG-Mesh: spec-class match, effect-mask filter, then solver-checked behavioral subtyping, cached and asynchronous; six-check ingestion gate. G7 target: indexed queries under 5 ms p99 on 100,000 nodes.

Native programs, locked down

Proven code compiles to native programs for PCs, Macs and WebAssembly, each allowed to touch only what it declares.

</>Proofs erased; proven facts become nsw, nuw, inbounds. G4 target: within 20% of clang -O2 C. OS sandbox manifest per target.

Honest by design

It never calls a guess a proof, never calls a measurement a guarantee, and says exactly what it trusts.

</>Measured (BUDGET) is never reported as proven (COST); release proofs need two solvers to agree; the trusted computing base is listed in the spec.

For the expert · Roadmap
For the expert

A verifier is only as good as its worst bug. VeriGraph attacks its own.

In plain words: it assumes its own checker can be wrong, and says what is still unsolved.

How soundness is engineered
  • Two solvers agree. z3, cvc5 and bitwuzla run as separate processes over SMT-LIB2; a release proof needs two of them to agree.
  • Every solver model is replayed in the reference interpreter, first with the model’s own values, then with the real code. A model that fails the first replay is a verifier bug, and it stops the build.
  • No empty proofs. A contract that no input can satisfy is rejected as vacuous.
  • Exact formulas. Integer terms in contracts become bit-vectors wide enough never to overflow, so no query needs the Int or Real sorts. Program arithmetic names its mode: checked, wrapping or saturating.
  • The verifier is attacked on every change: a known-bad corpus, mutation testing, differential testing of native and WASM builds against the interpreter, and fuzzing.
  • Bit-exact floats on every target: one canonical NaN, no fast-math, no flush-to-zero; checked entry points pin the floating-point environment.
  • Proofs survive tuning. Learnable parameters are proven over their whole declared range.
Can it prove speed?

No, and it does not pretend to. Operation counts and memory are proven (COST); wall-clock latency is measured per target (BUDGET).

Questions an expert will ask
What if the AI writes the wrong promise?

The spec rates this risk likely and severe. The promise is read back in plain English for a human to confirm, and vacuous promises are rejected. Closing the rest of the intent gap is research track R-14. OPEN

Why trust the solvers and LLVM?

They are in the trusted base, listed openly. Two solvers must agree on release proofs, and builds are tested against the interpreter with and without proof facts. Checkable proof certificates are research track R-05. OPEN

What about loops and timeouts?

Loops are bounded combinators with a mandatory invariant, checked by one base case and one inductive step; every query stays quantifier-free. A timeout is never a proof: the operation must sit behind an explicit runtime guard, counted in every build.

How is this different from Dafny or Verus?

It reuses proven ideas: SMT-checked contracts (Dafny, Verus), content-addressed code (Unison), bounded translation validation (Alive2). The difference: every query is quantifier-free by construction, with no triggers to tune, and the format, diagnostics and proof cache are built for agents that repair code unattended.
