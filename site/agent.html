Chapitre 8 · La boucle agent

La boucle agent, prouver plutôt qu'espérer.

Un modèle de langage ne devine pas si un programme est sans débordement ; il écrit une ébauche, lit les diagnostics typés et les contre-exemples reproductibles de vg, et répare jusqu'à ce que les solveurs prouvent chaque obligation.

  • vg-decode

Lecture : 14 minPrérequis : chapitres 3, 5 et 6

8.1Pourquoi VeriGraph est conçu pour les agents

Dans un langage classique, le compilateur répond souvent par des lignes de texte ambiguës, et les tests ne couvrent que les cas imaginés par l'auteur ou le modèle. VeriGraph renverse ce rapport : chaque décision d'architecture de docs/00-vision.md et de docs/15-agent-interface.md est évaluée selon ce qu'elle permet à un agent autonome d'accomplir sans intervention humaine intermédiaire.

Analogie

Travailler avec un langage textuel classique pour un modèle, c'est conduire dans le brouillard en espérant qu'aucun panneau ne manque. Avec VeriGraph, la route est bordée de capteurs précis : à la moindre sortie de voie, l'outil renvoie la coordonnée exacte du pneu qui mord la ligne (le contre-exemple et la tranche causale) et refuse tout simplement de livrer le véhicule tant que les capteurs ne sont pas au vert.

Huit invariants fondent cette approche IA-native (docs/00-vision.md), traduits dans l'interface par sept règles strictes (docs/15-agent-interface.md) :

  • Tout jugement est une donnée JSON typée. Erreurs, verdicts, contre-exemples et coûts utilisent un schéma stable et des codes immuables (VG-P…, VG-S…, VG-T…, VG-E…, VG-C…, VG-V…), sans journaux bruts de solveur.
  • Localisation dans les mots de l'agent. Chaque diagnostic cite le label du nœud (@soft_knee), le port tel qu'écrit (%4), le nom de paramètre, la ligne et la colonne — ainsi l'agent sait exactement quoi éditer.
  • Raisonnement local par contrat. Les types se déduisent opérande par opérande, et un appelant est prouvé uniquement à partir du contrat de l'appelé, jamais de son corps. Un agent peut donc réparer un nœud à la fois.
  • Texte vérifiable préfixe par préfixe. Chaque port et chaque label sont définis avant d'être utilisés (ADR 0005), ce qui autorise une validation incrémentale dès les premiers jetons générés.
  • Labels locaux au lieu d'empreintes inventées. Un modèle de langage ne sait pas calculer un hachage BLAKE3 ; il écrit @nom et laisse la chaîne d'outils calculer et épingler les empreintes canoniques.
  • Plus petite preuve suffisante et honnêteté des verdicts. En cas d'échec, un seul contre-exemple reproductible, une seule tranche élaguée et une condition diff sont renvoyés ; unknown reste toujours distinct de proven et de counterexample.

8.2La boucle générer → vérifier → réparer

Pour un modèle hébergé (Claude, Gemini, GPT), le dialogue avec VeriGraph prend la forme d'une boucle outillée : formuler une carte de contrat, interroger le registre VG-Mesh pour réutiliser les briques existantes, rédiger un brouillon en VG-Sym, passer vg_check (gratuit et instantané), appeler vg_verify et réparer selon le verdict reçu, dans une limite de cinq tours sans progrès avant d'escalader ou de changer d'approche.

8.4Ce qu'enseigne le skill de synthèse

Mettre des outils à disposition d'un modèle ne suffit pas : il doit savoir dans quel ordre les appeler et comment interpréter chaque verdict. C'est le rôle du fichier skills/verigraph-synthesis/SKILL.md, distribué automatiquement avec le plugin Antigravity et injecté dans le prompt système de vg loop.

  1. Carte de contrat d'abord

    Avant d'écrire la moindre opération, l'agent rédige une carte résumant entrées, sorties, effets, PRE, POST, COST, BUDGET, paramètres LEARNABLE et requêtes Mesh. Il fait valider par l'humain le contrat lui-même (ou contract_text une fois pris en charge par vg_check), afin que ce qui est confirmé soit exactement ce qui sera prouvé.

  2. Consulter VG-Mesh avant de réinventer

    Pour le hachage, les codecs, le tri ou l'algèbre linéaire, le skill impose d'appeler vg_mesh_query et de lier les candidats existants par @MESH_QUERY.

  3. Ébaucher des noyaux purs

    Les calculs vivent dans des nœuds purs (EFFECTS: []) et de taille fixe ; les effets et handles restent confinés à un mince nœud racine.

  4. Nettoyer avec vg_check, puis prouver avec vg_verify

    Une fois les erreurs statiques éliminées, l'agent suit une table de décision stricte par verdict : corriger le corps ou PRE sur counterexample, renforcer le POST d'un appelé sur contract_gap, découper ou ajouter un invariant sur unknown, affaiblir PRE sur vacuous — sans jamais affaiblir POST sans accord explicite.

Le skill enseigne aussi les idiomes de VG-Sym qui passent le solveur du premier coup. Survolez ou sélectionnez les zones soulignées de ce motif tiré de skills/verigraph-synthesis/SKILL.md :

NODE @safe_div {
  SIGNATURE: (x: i32, d: i32) -> (i32);
  EFFECTS: [];
  CONTRACT {
    PRE:  !(x == -2147483648 && d == -1);
    POST: (d == 0 ==> result == 0) && (d != 0 ==> result == x / d);
  }
  BODY {
    %0 = NE(d, 0:i32);
     %1 = SELECT(%0, d, 1:i32);
    %2 = DIV.checked(x, %1);
    %3 = SELECT(%0, %2, 0:i32);
    RETURN(%3);
  }
}

8.5La boucle hébergée et les paliers de décodage

Pour évaluer objectivement des modèles sur benchmarks/synthesis, VeriGraph intègre le harnais boucle hébergée vg loop (crates/vg-cli/src/hosted.rs). Le modèle reçoit trois outils : vg_check (gratuit), vg_verify (chaque appel compte pour un tour de réparation, jusqu'à --rounds) et submit. À la soumission, un correcteur indépendant (grader) ne fait aucune confiance aux affirmations du modèle : il re-vérifie le module, construit un nœud enveloppe @vg_reference qui appelle la soumission via CALL_HASH pour prouver qu'elle raffine le contrat de référence de la tâche (PRE_ref ⇒ PRE_cand et PRE_ref ∧ POST_cand ⇒ POST_ref), puis exécute les vecteurs de test dans vg-interp.

Afin de tester ce correcteur sans appel réseau payant, vg loop accepte l'option --replay SCRIPT.json. Nous l'avons exécuté lors de la génération des données de cette page sur les trois variantes du banc 03_midpoint_u32 (issues de crates/vg-cli/tests/hosted_loop.rs) :

8.6L'histoire M1 : du texte libre au limiteur audio

Le jalon M1 repose sur un scénario concret décrit dans examples/audio_limiter.prompt.md : partir d'une demande en langage naturel, faire échouer une première ébauche avec un contre-exemple réel, puis prouver la version corrigée reliée à un SHA-256 issu de VG-Mesh. Voici la demande exacte du dépôt :

« Write a verified real-time audio limiter and packet integrity module that takes a 512-sample stereo FP32 audio buffer, clamps peaks smoothly using a learnable knee threshold so no sample ever exceeds [-1.0, 1.0], computes a SHA-256 integrity digest of the output frame, and runs in under 500 microseconds with zero heap allocation. »

Remarquez la précision importante de examples/audio_limiter.prompt.md : « runs in under 500 microseconds » plutôt que « guarantees execution in under 500 microseconds ». La latence mesurée relève d'un BUDGET (observé sur machine cible), jamais d'une preuve formelle, tandis que l'absence d'allocation dynamique relève du COST (heap_bytes == 0 && arena_bytes == 0).

Limite actuelle

Bien que le harnais vg loop, les 30 tâches de référence dans benchmarks/synthesis et la preuve complète de examples/audio_limiter.vgs fonctionnent localement, le jalon G5 est actuellement en échec (reports/gate-g5.md) : la campagne sur les 30 tâches avec un modèle API payant n'a pas encore été lancée (no reports/g5/results.json). Par estimation — et non mesure — une exécution complète sur 30 tâches avec Claude Opus 5.5 consommerait environ 1,5 million de jetons en entrée et 150 000 en sortie, soit autour de 9 $ avant mise en cache du préfixe (docs/guide/cli.md).

8.7Vérifiez votre compréhension

Question 1

Dans vg loop, un modèle soumet une implémentation de @midpoint_u32 avec POST: true qui vérifie sans erreur et réussit tous les tests unitaires. Que décide le correcteur ?

C'est exactement le cas b_weak de crates/vg-cli/tests/hosted_loop.rs (et de site/data/agent.json) : un contrat trop faible est vérifiable en lui-même, mais échoue au raffinement du contrat de référence. Une unsound_accept désignerait un nœud vérifié qui violerait son propre POST sur un test.

Question 2

Pourquoi le vérificateur incrémental de vg-decode (palier 2) peut-il valider un préfixe de code VG-Sym au fil des jetons ?

Grâce à l'ADR 0005, vg-decode::Prefix connaît à tout instant l'ensemble des ports, labels et opcodes valides pour la suite immédiate, en 23 µs au p99 (PROGRESS.md, 2026-11-23).

Question 3

Lorsqu'un appel vg_verify via MCP renvoie un contre-exemple, que vaut isError dans la réponse MCP ?

Comme le précise docs/guide/mcp.md, isError reste à false même quand "ok": false, pour que l'agent lise le rapport structuré et passe au tour de réparation suivant.

À retenir

VeriGraph transforme le dialogue avec une IA en boucle fermée par la preuve : l'agent s'appuie sur huit outils MCP typés, un skill orienté contrat, des contre-exemples concrets avec tranche causale, et un correcteur indépendant qui vérifie chaque soumission face à un contrat de référence. Le décodage contraint (vg-decode) complète cette boucle côté modèles locaux.
