Chapitre 4 · vg-types

Types, effets et capacités.

Avant qu'un solveur SMT n'ouvre le moindre fichier de preuve, vg-types répond à trois questions : de quelles données parle-t-on, dans quel ordre les effets de bord surviennent-ils, et quelles ressources externes le programme a-t-il le droit de toucher ?

  • vg-rt
Lecture : 15 min Prérequis : chapitre 3

4.1Types scalaires, composés et raffinements

Dans VeriGraph, le typage local garantit qu'une opération déduit ses résultats uniquement de son opcode, de son mode et des types de ses opérandes — jamais du contexte d'appel ou d'une inférence globale. Aucune conversion implicite n'existe : additionner un u32 et un u64 est immédiatement rejeté (VG-T0102), et une comparaison ordonnée doit porter le suffixe exact de ses opérandes (.s, .u ou .f, sinon VG-T0103). Les seules annotations demandées dans le corps concernent les constructeurs OK et ERR de Result<T, E>, car chaque branche ne connaît qu'une moitié du type somme (ADR 0004, sinon VG-T0115).

Au-delà des scalaires et collections, la signature accepte un type de raffinement écrit {x: T | φ}. Dans le MVP, un raffinement ne peut apparaître qu'au sommet de SIGNATURE (jamais imbriqué dans un tableau ou un tuple, sinon VG-T0116) : placé sur un paramètre, le prédicat φ s'ajoute automatiquement à PRE ; placé sur un résultat, il s'ajoute à POST. Selon docs/adr/0001-format-encodings.md, les deux écritures produisent exactement le même nœud canonique et la même empreinte.

4.2Les effets et le jeton linéaire Eff

Un graphe de flot de données pur n'a ni horloge ni notion d'« avant » et d'« après » : si deux instructions ne dépendent pas l'une de l'autre, le moteur d'exécution peut les évaluer dans n'importe quel ordre, et la canonicalisation fusionne les copies identiques. Pour les entrées/sorties, c'est inacceptable : lire un fichier puis écrire le résultat doit suivre un ordre unique, et deux écritures identiques ne doivent jamais fusionner.

VeriGraph résout ce problème grâce à un jeton d'effet linéaire de type Eff. Chaque nœud dont le masque EFFECTS contient autre chose que ARENA reçoit Eff comme premier paramètre et retourne un nouveau jeton Eff comme premier résultat (VG-E0103). Chaque valeur Eff doit être consommée exactement une fois (VG-E0102) : la lâcher ou la passer à deux opérations en parallèle est une erreur de compilation immédiate.

Quant au masque EFFECTS lui-même, c'est un ensemble sur 32 bits (docs/04-types-effects.md). L'ensemble vide [] signifie PURE, et l'absence du bit NONDET garantit le déterminisme. Lorsqu'un nœud appelle un autre nœud, son masque doit contenir tous les bits de l'appelé (transitivité vérifiée par VG-E0101).

Attention — Pourquoi PURE et SIMD ne sont pas des bits (E-09)

La spécification d'origine traitait PURE comme la valeur 0x0000 listée à côté d'autres bits et rangeait SIMD dans les effets. L'erratum E-09 corrige les deux : PURE est simplement l'ensemble vide [], et SIMD est un choix de génération de code (un appelant scalaire peut appeler un noyau vectorisé sans déclarer d'effet).

Le module réel tests/corpus/alpha/a45_file_read_write_chain/01.vgs montre comment le jeton e0: Eff traverse @read_header puis @write_payload avant de ressortir en %902 :

module a45_file_read_write_chain;

NODE @read_header [intent: "Read header slice from file"] {
  SIGNATURE: (e: Eff, fin: FileIn) -> (Eff, Result<Slice<u8>, u32>);
  EFFECTS: [ARENA, FILE_READ];
  CONTRACT {
    COST: arena_bytes <= 16;
  }
  BODY {
    %0, %1 = FILE_READ(e, fin, 16:u64);
    RETURN(%0, %1);
  }
}

NODE @write_payload [intent: "Write byte slice to file"] {
  SIGNATURE: (e: Eff, fout: FileOut, bytes: Slice<u8>) -> (Eff, Result<u64, u32>);
  EFFECTS: [FILE_WRITE];
  CONTRACT {
    COST: ops <= 2;
  }
  BODY {
    %0, %1 = FILE_WRITE(e, fout, bytes);
    RETURN(%0, %1);
  }
}

NODE @relay_block [intent: "Read and write chain"] {
  SIGNATURE: (e0: Eff, fin: FileIn, fout: FileOut) -> (Eff, Result<u64, u32>);
  EFFECTS: [ARENA, FILE_READ, FILE_WRITE];
  CONTRACT {
    COST: arena_bytes <= 16;
  }
  BODY {
    %900 = IDENTITY([65, 66]:Array<u8, 2>);
    %905 = SLICE(%900, 0:u64, 2:u64);
    %901, %903 = CALL_HASH(@read_header, e0, fin);
    %902, %904 = CALL_HASH(@write_payload, %901, fout, %905);
    RETURN(%902, %904);
  }
}

4.3Capacités et bac à sable système

Déclarer FILE_READ dans EFFECTS ne donne accès à aucun chemin du disque. Pour lire un fichier, un nœud doit recevoir une poignée de capacité (FileIn, FileOut ou Clock dans le MVP) transmise explicitement depuis la racine du programme. Un bit d'effet sans poignée n'accorde aucun droit ; à l'inverse, accepter une poignée sans déclarer le bit d'effet correspondant est refusé par vg-types (VG-E0104). De plus, Eff et les poignées ne peuvent jamais être rangés dans un tableau, un tuple ou un Result, ni passés à un noyau de boucle (VG-T0119).

Pour que cette discipline tienne aussi à l'échelle du processus compilé (E-19), vg build émet un manifeste de bac à sable (<label>.manifest.toml) et le runtime C vg-rt applique une règle stricte décrite dans docs/adr/0011-os-sandbox.md : ouvrir d'abord les descripteurs autorisés, puis verrouiller le processus avant d'appeler la racine.

Analogie

C'est le principe d'une salle blanche : l'intendant dépose sur la table les deux classeurs autorisés par le bon de commande (argv), puis verrouille définitivement toutes les portes menant aux archives avant que l'opérateur n'entre en scène.

Limite actuelle

Selon docs/adr/0011-os-sandbox.md (proposé le 2026-11-24), le confinement utilise sandbox_init sur macOS, Landlock + seccomp sur Linux, et les pré-ouvertures WASI sur WASM ; si sandbox_init venait à être retiré par Apple ou si un noyau Linux n'avait pas Landlock, le binaire quitterait avec le code 5 plutôt que de tourner sans bac à sable. Par ailleurs, vg build génère aujourd'hui les liaisons argv (pas encore les chemins fixed ni stdin nommé), et les effets réseau (NET_READ, NET_WRITE) restent hors MVP.

4.4Arène d'appel et comptage COST

Dans le MVP (ADR 0003), les types à taille fixe (scalaires, Array, Tensor) vivent sur la pile et n'allouent jamais de tas. Seules les tranches Slice<T> de longueur dynamique — produites par FILE_READ, CONCAT de tranches, SIMD_MAP ou GENERATE sur une taille non littérale — allouent dans une unique arène d'appel fournie au point d'entrée et libérée à la sortie. Toute opération de ce type exige le bit ARENA (VG-E0106), mais sans nécessiter de jeton Eff car l'ordre des allocations est invisible.

vg-types calcule symboliquement les expressions exactes d'ops et d'arena_bytes (COST), tandis que BUDGET (comme latency_p99_us) reste une cible mesurée et interdite dans COST (VG-C0106, errata E-10 et E-15).

Pour aller plus loin : mise à jour en place et règle d'échappement VG-T0120

Un UPDATE(xs, i, v) sur une tranche s'effectue en place (zéro copie) uniquement si xs provient d'une opération allouante possédant une seule utilisation ; toute autre tranche (vue SLICE, AS_BYTES ou paramètre d'entrée) est copiée dans l'arène. De plus, comme une valeur fixe locale disparaît au retour du nœud, vg-types interdit qu'une vue retournée puisse pointer vers une donnée locale (VG-T0120) : pour renvoyer les octets d'un tableau local, renvoyez directement le tableau à taille fixe.

4.6La frontière de confiance : tester zoom.wasm en direct

Une preuve ne vaut que si ses hypothèses tiennent. Or un programme appelant un binaire compilé depuis l'extérieur (JavaScript, un shell ou du code C) n'est pas vérifié par VeriGraph. Pour éviter qu'une entrée invalide ne pénètre dans le code optimisé, vg-codegen génère pour chaque nœud exporté une entrée vérifiée (ADR 0009).

Avant d'appeler le corps interne, cette entrée vérifiée contrôle que les octets booléens valent 0 ou 1, normalise tout NaN, installe l'environnement d'arrondi IEEE 754 par défaut, et évalue PRE. Si une seule condition échoue, le binaire s'interrompt immédiatement avec le code de sortie 1 sans exécuter le corps.

Testez ci-dessous le vrai module WebAssembly site/wasm/zoom.wasm (compilé depuis @zoom dans site/vg/weblib.vgs), dont la précondition impose cx ∈ [-2.5, 1.5], cy ∈ [-1.5, 1.5], scale ∈ (0.0, 0.02], px < 256 et py < 192.

4.7Vérifiez votre compréhension

Question 1

Un nœud pur (EFFECTS: []) reçoit un paramètre fin: FileIn et le retourne sans jamais appeler FILE_READ. Que fait vg check ?

Comme le montre le cas e0104_file_in_without_bit.vgs dans l'atelier ci-dessus, déclarer une poignée sans son bit d'effet correspondant est toujours rejeté par vg-types (VG-E0104).

Question 2

Dans quel ordre vg-rt configure-t-il les accès fichiers et le bac à sable d'un exécutable compilé ?

Une fois le bac à sable activé (sandbox_init ou Landlock), aucun nouveau fichier ne peut plus être ouvert. vg-rt ouvre donc les descripteurs autorisés d'abord, puis droppe tous les autres droits avant d'appeler le nœud racine (ADR 0011).

Question 3

Que renvoie site/wasm/zoom.wasm si un appelant JavaScript non vérifié lui passe scale = 0.05 (alors que PRE impose scale <= 0.02) ?

L'entrée vérifiée (ADR 0009) contrôle PRE à la frontière de confiance. Dès qu'une entrée viole PRE, le binaire sort avec le code 1, comme vérifié dans site/test.mjs.

À retenir

vg-types garantit avant toute preuve que chaque opération est bien typée, que les effets suivent une chaîne linéaire unique sur Eff, que l'autorité reste confinée aux poignées transmises jusqu'au bac à sable OS, et que les entrées externes sont contrôlées à la frontière. Dans le chapitre suivant, nous entrons au cœur des preuves formelles avec vg-smt.
