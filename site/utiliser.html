12.1Installer la chaîne d'outils

Vous voulez passer des principes à la pratique sur votre propre machine ? VeriGraph s'articule autour d'un seul exécutable, vg, compilé en Rust, qui pilote ensuite des solveurs SMT externes et un compilateur C/LLVM. Aucun démon caché ne tourne en permanence : vg lance Z3, Bitwuzla, cvc5 ou clang comme des sous-processus isolés dont les versions sont consignées dans rust-toolchain.toml et toolchain.lock.

Analogie

Voyez vg comme un chef d'atelier : il lit votre plan en VG-Sym, fait inspecter chaque pièce par un ou deux vérificateurs indépendants (les solveurs SMT), puis confie la fabrication à clang seulement lorsque tous les tampons de conformité sont réunis.

Dans la version actuelle (docs/guide/install.md et toolchain.lock), l'outil principal est développé et testé en priorité sur macOS Apple Silicon (aarch64-apple-darwin). Sur Linux x86_64, l'analyse (vg check), la preuve (vg verify), l'interpréteur (vg run) et le serveur MCP (vg mcp) fonctionnent également, et vg build lie les binaires natifs dès que zig est présent.

Choisissez votre système ci-dessous pour installer les dépendances, compiler vg et vérifier que la chaîne répond :

Installez d'abord les outils en ligne de commande Xcode (xcode-select --install) et Rust via rustup, puis les solveurs et cibles WebAssembly via Homebrew :

brew install z3 bitwuzla llvm wasi-libc wasi-runtimes wasmtime zig

Notez que sur macOS antérieur à Xcode 27, le compilateur clang d'Apple ne contient pas la cible wasm32 ; vg détecte alors automatiquement le clang de Homebrew LLVM (docs/guide/install.md). Pour compiler et installer vg dans ~/.cargo/bin depuis la racine du dépôt :

cargo install --path crates/vg-cli --locked

Si vous travaillez directement dans le dépôt sans installer globalement, compilez le binaire de publication et vérifiez le premier exemple :

cargo build --release -p vg-cli
./target/release/vg check examples/quickstart.vgs
./target/release/vg verify examples/quickstart.vgs

Installez Rust 1.90.0 avec rustup (qui lit rust-toolchain.toml automatiquement), puis récupérez l'archive officielle de Z3 5.4.1 depuis les sorties GitHub de Z3 (comme le fait la CI dans .github/workflows/ci.yml) et placez z3 dans /usr/local/bin ou sur votre PATH.

curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
cargo install --path crates/vg-cli --locked

vg cherche chaque solveur dans /opt/homebrew/bin, puis /usr/local/bin, puis sur PATH. Vérifiez votre installation avec :

vg check examples/quickstart.vgs
vg verify examples/quickstart.vgs

12.2Votre premier nœud pas à pas

Le tutoriel officiel (docs/guide/tutorial.md) propose de partir d'un petit module, de le contrôler, de le prouver, de l'exécuter puis de le compiler — avant d'observer ce qui se passe lorsqu'un contrat est violé. Nous rejouons ici exactement ce parcours sur deux fichiers du dépôt : examples/quickstart.vgs (sain) et examples/soft_knee_draft.vgs (boggué).

Voici deux nœuds extraits mot pour mot de examples/quickstart.vgs : @add_sat additionne deux octets avec saturation, et @soft_knee compresse en douceur un échantillon audio flottant dans [-1, 1].

NODE @add_sat [intent: "Add two bytes, saturating at 255"] {
  SIGNATURE: (a: u8, b: u8) -> (u8);
  EFFECTS: [];
  CONTRACT {
    POST: result >= a && result >= b && (a + b <= 255 ==> result == a + b);
  }
  BODY {
    %0 = ADD.sat(a, b);
    RETURN(%0);
  }
}

NODE @soft_knee [intent: "Soft-knee clip of one sample into [-1, 1]"] {
  SIGNATURE: (x: f32, knee: f32) -> (f32);
  EFFECTS: [];
  CONTRACT {
    PRE:  is_finite(x) && knee >= 0.5 && knee <= 0.99;
    POST: result >= -1.0 && result <= 1.0 && ((x >= 0.0) == (result >= 0.0));
  }
  BODY {
    %0  = FABS(x);
    %1  = FSUB(%0, knee);
    %2  = FMAX(%1, 0.0:f32);
    %3  = FSUB(1.0:f32, knee);
    %4  = FDIV(%2, %3);
    %5  = FADD(1.0:f32, %4);
    %6  = FDIV(1.0:f32, %5);
    %7  = FSUB(1.0:f32, %6);
    %8  = FMA(%3, %7, knee);
    %9  = FCOPYSIGN(%8, x);
    %10 = LE.f(%0, knee);
    %11 = SELECT(%10, x, %9);
    %12 = FCLAMP(%11, -1.0:f32, 1.0:f32);
    RETURN(%12);
  }
}
  1. Contrôler la syntaxe, les types et les empreintes (vg check)

    vg check analyse le texte VG-Sym, met chaque graphe sous forme canonique, calcule son empreinte BLAKE3 (node_hash) et vérifie les types et effets. À ce stade, rien n'est encore prouvé mathématiquement.

  2. Prouver toutes les obligations (vg verify)

    vg verify décompose chaque nœud en obligations de preuve : non-vacuité de PRE, sûreté des opérations partielles (ADD.no_overflow, FCOPYSIGN.sign, FCLAMP.bounds…), et chaque conjonction de POST. Un solveur doit répondre unsat à la négation de l'objectif.

  3. Tester concrètement dans l'interpréteur (vg run)

    vg run exécute le nœud dans l'interpréteur de référence vg-interp. Les flottants et entiers 64 bits sont passés entre guillemets ("3e38", "0.5") pour ne perdre aucun bit en JSON. La réponse indique pre, post et les sorties.

  4. Compiler en binaire natif sans gardes (vg build)

    vg build re-vérifie le nœud et ses dépendances (en réutilisant le cache dans .vg/proofs), efface les assertions prouvées et génère un exécutable via clang. Comme toutes les obligations sont prouvées, le champ residual_guards vaut 0.

Provoquer un bogue et lire le contre-exemple

Que se passe-t-il si le corps contient une erreur subtile ? Dans examples/soft_knee_draft.vgs, l'auteur a calculé %6 = FDIV(%4, %5) c'est-à-dire t / (1 + t). Sur les valeurs courantes, tout semble parfait. Mais dès que x approche la limite des flottants 32 bits (-3.4028235e38), t déborde vers +inf, puis inf / inf produit NaN — et FCLAMP propage NaN au lieu de borner à [-1, 1].

12.3La boucle de travail au quotidien

En pratique, travailler avec VeriGraph suit un cycle court et déterministe. Tant qu'une preuve échoue, vous ne compilez pas à l'aveugle : vous inspectez le contre-exemple concret fourni par vg explain ou l'extrait de code dans votre éditeur, vous corrigez soit le corps (bogue d'implémentation), soit PRE (hypothèse manquante aux frontières), soit le contrat d'un nœud appelé (contract gap).

12.4Utiliser VeriGraph avec un agent IA

Plutôt que de taper chaque nœud à la main, vous pouvez confier la rédaction à un assistant IA tout en gardant la même barrière mathématique : l'agent s'adresse à la chaîne d'outils via le protocole MCP (Model Context Protocol) lancé par vg mcp sur entrée/sortie standard, et s'appuie sur le skill skills/verigraph-synthesis/SKILL.md pour suivre la méthode « contrat d'abord, puis preuve et réparation ».

Le dépôt fournit un installateur complet dans editors/antigravity/install.sh. En une commande, il compile et installe vg dans ~/.cargo/bin, empaquette l'extension reproductible target/antigravity/verigraph-0.1.0.vsix, l'installe dans Antigravity IDE, et déploie le plugin dans ~/.gemini/config/plugins/verigraph (avec le skill et la configuration MCP) :

editors/antigravity/install.sh

Si vous préférez déclarer uniquement le serveur MCP manuellement dans ~/.gemini/config/mcp_config.json :

{ "mcpServers": { "verigraph": { "command": "/Users/you/.cargo/bin/vg", "args": ["mcp"] } } }

Ajoutez un fichier .mcp.json à la racine de votre projet contenant des sources .vgs, en donnant le chemin absolu vers vg (un client lancé depuis une interface graphique n'hérite pas toujours du PATH de votre shell) :

{ "mcpServers": { "verigraph": { "command": "/Users/you/.cargo/bin/vg", "args": ["mcp"] } } }

Chargez également skills/verigraph-synthesis/SKILL.md dans les instructions du projet pour que le modèle sache lire les codes VG-… et ne livre jamais un nœud non prouvé.

Tout client compatible avec la spécification MCP 2025-06-18 sur transport stdio peut démarrer vg mcp. Le serveur expose les huit outils décrits dans docs/15-agent-interface.md (vg_check, vg_verify, vg_explain, vg_mesh_query, vg_mesh_publish, vg_run, vg_build et vg_lift) ; le chapitre 8 détaille chacun de leurs schémas.

Dans Antigravity IDE (et tout éditeur compatible VS Code), l'extension verigraph.verigraph (version 0.1.0, déclarée dans editors/antigravity/extension/package.json) active la coloration syntaxique sur les fichiers .vgs, lance vg check à l'ouverture et à chaque sauvegarde, et ajoute trois boutons dans la barre de titre de l'éditeur : Verify File (✓), Run Node… (▶) et Build Node… (paquet). Cinq réglages permettent d'ajuster le chemin de vg (verigraph.vgPath), la vérification automatique à l'enregistrement (checkOnSave par défaut à true, verifyOnSave à false), le délai d'attente du solveur (verifyTimeoutMs, 10 000 ms par défaut) et le dossier de sortie (buildOutputDir, target/vg).

Attention

Contrairement à la ligne de commande qui propose l'échappatoire explicite --unverified pour un humain, l'outil MCP vg_build refuse toujours de compiler un nœud dont une obligation reste non prouvée. De plus, lors de l'appel par un agent, fournissez un chemin out_dir absolu (docs/guide/mcp.md).

Les commandes JSON (check, verify, run, build) partagent les codes de sortie suivants : 0 lorsque "ok": true, 1 lorsque "ok": false (le JSON explique pourquoi), et 2 si les arguments sont invalides. Les binaires compilés par vg build utilisent quant à eux six codes précis (docs/guide/cli.md) :

Code du binaire compiléSignification
0Succès ; les résultats sérialisés (docs/13) sont écrits sur stdout.
1Les entrées violent la précondition PRE à l'entrée vérifiée (checked entry).
2Les octets d'entrée sont mal formés : trop courts, ou NaN non canonique.
3L'arène mémoire allouée au nœud est épuisée.
4Échec d'une garde à l'exécution (uniquement dans un binaire compilé avec --unverified).
5Argument de handle manquant ou impossible à ouvrir, ou échec d'application du bac à sable OS (ex. noyau Linux sans Landlock).

12.6Dépannage et état du projet

Voici les sept situations les plus fréquentes recensées dans docs/guide/troubleshooting.md lorsque vous commencez à utiliser VeriGraph :

vg verify répond error ou unknown pour chaque obligation

Z3 est introuvable ou ne se lance pas. vg cherche successivement /opt/homebrew/bin/z3, /usr/local/bin/z3 puis z3 dans PATH. Vérifiez z3 --version (version attendue : 5.4.1).

Une obligation revient unknown avec le code VG-V0004

Le solveur a dépassé son budget de temps. L'arithmétique entière non linéaire (produit ou division de deux variables, comme result == a / b sur des u32) en est la cause habituelle. Énoncez une propriété plus faible mais suffisante pour les appelants (comme result <= a && (b == 1 ==> result == a) dans docs/guide/tutorial.md), découpez la conjonction en clauses plus petites, ou augmentez --timeout.

Un contre-exemple affiche 3e38, -3.4028235e38 ou nan

Le domaine f32 inclut les infinis, NaN et les nombres proches de ±3.4e38, et le solveur les essaie tous. Ajoutez explicitement is_finite(x) et les bornes utiles dans PRE aux frontières, et privilégiez des formules qui restent finies aux extrêmes.

vg check signale VG-P0001 près de % ou sur un accès imbriqué

L'analyseur lexical interprète x%2 comme l'identifiant x suivi du port %2 : écrivez x % 2 avec des espaces. De même, t.0.1 est découpé en t, . et 0.1 : écrivez (t.0).1.

Erreurs statiques VG-S0102 ou VG-S0004

VG-S0102 signifie qu'un mode manque sur une opération entière ou une comparaison ordonnée : il n'y a aucune valeur par défaut, écrivez explicitement ADD.checked, ADD.wrap ou ADD.sat, et LT.s, LT.u ou LT.f. VG-S0004 indique qu'un label est appelé avant sa définition : placez les noyaux et fonctions appelées au-dessus de leurs appelants.

vg build produit "linked": false ou le binaire quitte avec le code 5

Pour x86_64-unknown-linux-gnu ou wasm32-wasip1, "linked": false indique que l'éditeur de liens cible (zig, ou Homebrew llvm + wasi-libc + wasi-runtimes) est absent ; le fichier objet est tout de même émis. À l'exécution, le code de sortie 5 signifie qu'un argument de handle manque ou qu'un bac à sable OS (Landlock sous Linux 5.13+, sandbox_init sur macOS) n'a pas pu être appliqué : un programme VeriGraph ne s'exécute jamais sans confinement.

L'identifiant d'obligation cite un port %10 qui n'est pas le même que dans mon fichier

La canonicalisation trie, renumérote les opérations et supprime les nœuds morts (VG-W0001). Utilisez vg disasm <HASH> après vg asm pour inspecter la numérotation canonique exacte.

12.7Vérifiez votre compréhension

Question 1

Vous venez d'écrire un nœud et vous lancez vg check fichier.vgs, qui renvoie "ok": true. Que pouvez-vous affirmer ?

vg check ne lance aucun solveur SMT : seule la commande vg verify (ou vg build, qui l'appelle) prouve les obligations.

Question 2

Un agent connecté à vg mcp tente d'appeler vg_build sur un nœud qui comporte une obligation unknown. Que fait le serveur MCP ?

Règle fondamentale de VeriGraph : unknown n'est jamais une preuve, et vg_build via MCP ne livre jamais un nœud non prouvé (docs/guide/mcp.md).

Question 3

Quelle différence existe-t-il entre l'état des jalons G3 et G4 au 2026-11-24 ?

D'après reports/gate-g3.md et reports/gate-g4.md, G3 satisfait ses critères et attend la revue du propriétaire, tandis que G4 échoue sur matmul (1,378), sha256 (2,640) et mandelbrot (4,477) ainsi que sur l'absence de mesures x86_64.

À retenir

La chaîne d'outils VeriGraph tient dans un binaire unique (vg) qui vérifie statiquement (check), prouve par solveurs SMT (verify), explique les réfutations par tranches causales (explain), interprète (run), compile sans gardes résiduelles (build) et s'ouvre aux agents via vg mcp et Antigravity IDE. Chaque chiffre publié reste traçable : ce qui est prouvé est prouvé, et ce qui ne l'est pas encore (G4, G5) est assumé explicitement.
