Chapitre 7 · vg-codegen · vg-rt

Du graphe au binaire, bit pour bit.

Une fois toutes les obligations prouvées, vg-codegen transforme le graphe canonique en LLVM IR textuel, efface les vérifications superflues et compile avec clang vers Linux x86_64, macOS ARM64 et WebAssembly WASI, en liant un petit runtime C qui enferme le binaire dans un bac à sable système.

7.1Six étapes du graphe vérifié au binaire

Dans un compilateur traditionnel, la sûreté repose sur des contrôles à l'exécution (bornes de tableaux, vérifications de débordement) ou sur l'hypothèse risquée qu'il n'y a aucun comportement indéfini. VeriGraph suit la voie inverse : parce que vg-smt a déjà démontré l'absence de débordement et d'accès hors bornes, vg-codegen peut retirer les gardes prouvées tout en conservant une frontière sûre à l'entrée du module.

Analogie · L'échafaudage retiré après le clavage

Les contrats et les obligations prouvées jouent le rôle d'un échafaudage qui garantit la géométrie d'une voûte pendant sa construction. Une fois la clef de voûte posée (UNSAT), l'échafaudage est démonté avant l'ouverture : ne restent que des instructions machine ajustées, et un portique de contrôle à l'entrée publique.

Pourquoi émettre de l'IR LLVM textuel plutôt que de lier l'API C++ d'une version précise de LLVM ? Parce que la syntaxe textuelle isole le compilateur Rust d'une dépendance lourde et permet d'inspecter directement le code envoyé à clang via l'option --emit-llvm. 7.2Effacement des preuves, entrée vérifiée et NaN canonique

L'effacement des preuves se voit concrètement en comparant le même calcul entier — %0 = ADD.checked(x, 1:u8); RETURN(%0); — compilé sous forme vérifiée (tests/corpus/good/g01_add_bounded.vgs, avec PRE: x < 255) puis compilé sans preuve grâce au drapeau --unverified (tests/corpus/bad/b01_add_overflow.vgs) :

Vérifié · g01_add_bounded.vgs —
Non vérifié · --unverified —

Dans la version prouvée, vg-codegen transmet la précondition via llvm.assume et émet un simple add nuw i8 %in0, 1, sans branchement. Avec --unverified, chaque opération partielle génère un test dynamique (llvm.uadd.with.overflow.i8) et un saut vers vg_trap_guard qui termine le processus avec le code 4 en cas de dépassement. L'outil MCP vg_build interdit d'ailleurs --unverified.

En parallèle, les rapports de compilation comptent dans residual_guards les ASSERT_GUARD dynamiques qui n'ont pas pu être prouvés toujours vrais : 0 sur g01_add_bounded et @midpoint, contre 1 sur un nœud contenant un ASSERT_GUARD dépendant d'une condition booléenne inconnue (ASSERT_GUARD.branch, qui est un branchement normal, n'est jamais compté comme garde résiduelle). Le drapeau --no-proof-facts permet enfin aux tests différentiels de compiler sans nsw/nuw/inbounds/llvm.assume afin de vérifier qu'aucun fait erroné n'a corrompu l'optimisation.

La frontière de confiance : l'entrée vérifiée (ADR 0009)

Un appelant C ou JavaScript externe n'est pas prouvé par VeriGraph. Chaque nœud exporté ou racine reçoit donc une entrée vérifiée (vg_<12 hex>) qui valide les octets d'entrée avant d'appeler vgi_<12 hex> : elle renvoie 0 en cas de succès, 1 si PRE échoue, 2 si un encodage est invalide (un Bool différent de 0/1 ou un NaN non canonique) et 3 si l'arène fournie est trop petite.

Avant d'exécuter le graphe, vg_fp_enter() sauvegarde le registre flottant de l'appelant (MXCSR mis à 0x1F80 sur x86_64, FPCR mis à 0 sur ARM64 Darwin ; WebAssembly n'a qu'un seul mode) pour imposer l'arrondi au plus près pair et interdire le vidage des sous-normaux vers zéro — indispensable lorsqu'un greffon audio appelle VeriGraph depuis un hôte configuré en flush-to-zero. Aucun drapeau -ffast-math ni contraction implicite (-ffp-contract=off) n'est jamais activé.

Un seul NaN en mémoire (ADR 0002)

LLVM et les architectures matérielles choisissent des motifs de NaN différents selon les opérandes. Pour que vg-interp, x86_64, ARM64 et WebAssembly produisent des octets identiques, toute valeur flottante susceptible d'être NaN est normalisée en NaN canonique (bit de signe nul, calme) dès qu'elle devient des octets en mémoire ou en sortie ; lorsque le vérificateur prouve qu'un flottant n'est jamais NaN (comme dans @soft_knee), cette comparaison est effacée :

Comment les types VG deviennent l'ABI C et où vit la mémoire

Chaque type VG correspond à une représentation C stable (docs/06-codegen-runtime.md) : Bool sur un octet (uint8_t), Array et Tensor en tableaux contigus ligne par ligne passés par pointeur, Slice<T> comme une paire { ptr, uint64_t len }, et Eff effacé à la compilation une fois l'ordre des effets figé. Les valeurs fixes de plus de 4 Kio passent dans un bloc scratch au début de l'arène d'appel plutôt que sur la pile, afin de protéger les fils secondaires dont la pile peut être réduite à 512 Kio.

7.4Le runtime vg-rt et le bac à sable système (ADR 0011)

Chaque binaire est lié avec runtime/vg_rt.c (~1 000 lignes de C compilées avec -ffp-contract=off). Au démarrage, vg-rt vérifie les capacités CPU et l'environnement flottant, alloue en une seule fois l'arène linéaire dimensionnée par la clause COST (vg_*_arena_bytes), ouvre uniquement les poignées déclarées dans le manifeste à partir de argv (code de sortie 5 si un fichier manque), puis appelle vg_rt_sandbox() avant d'entrer dans le nœud racine.

Le bac à sable applique une politique « tout refuser par défaut » adaptée au système : sur macOS, sandbox_init("(version 1)(deny default)", ...) laisse les descripteurs déjà ouverts lisibles mais bloque tout nouvel appel open avec EPERM ; sur Linux, Landlock (sans aucun droit fichier ni socket TCP) combiné à un filtre seccomp interdit socket avec EPERM et refuse de démarrer sur un noyau sans Landlock ; sous WASI, seuls les répertoires explicitement préouverts (wasmtime --dir) existent.

Limite actuelle · Bac à sable

Sous macOS, sandbox_init est déprécié par Apple : l'ADR 0011 précise que si Apple venait à le retirer, les binaires s'arrêteraient avec le code 5 plutôt que de s'exécuter sans confinement. De plus, d'après reports/gate-g4.md, les tests de refus sous macOS et WASM passent sur cet hôte ARM64, mais le test Linux (linux_sandbox_refuses_an_ungranted_file) n'a pas encore été exécuté sur un hôte Linux.

7.5Performances face à clang -O2 : état honnête

Supprimer les contrôles redondants et annoter l'IR LLVM suffit-il à égaler du C écrit à la main avec clang -O2 -ffp-contract=off ? Pas encore partout. La figure ci-dessous trace les mesures réelles de reports/bench/latest.md à l'aide de bar_chart.wasm ; l'objectif de la porte G4 est un ratio d'au plus 1,20× sur les deux cibles natives.

État honnête de la porte G4 (reports/gate-g4.md)

La porte G4 échoue actuellement. Sur Apple M3 Max (aarch64-apple-darwin), blend (0,78×) et crc32 (1,00×) atteignent l'objectif, mais trois noyaux dépassent 1,20× pour des raisons identifiées dans PROGRESS.md, 2026-11-24 :

  • matmul (1,38×) : matérialise GENERATE(@iota, 256) par cellule au lieu de fusionner générateur et pli.
  • sha256 (2,64×) : absorbe un octet par tour de FOLD_BOUNDED et recopie l'état de 96 octets quatre fois par octet (~290 octets de memcpy par octet de message).
  • mandelbrot (4,48×) : garde des SELECT sans branchement et deux normalisations NaN sur le tuple accumulateur pendant les 64 itérations, là où le C utilise un if (inside) très prévisible.

De plus, aucun benchmark ni test différentiel n'a encore été mesuré sur x86_64-unknown-linux-gnu sur cet hôte ARM64. En revanche, les sorties de tous les noyaux sont identiques octet pour octet au C, et 1 000 programmes générés (243 136 exécutions) concordent avec vg-interp sur ARM64 et WASM avec et sans faits de preuve.

7.6Démo en direct : le limiteur audio M1 (@limit_frame)

Le jalon M1 aboutit avec examples/audio_limiter.vgs. Son nœud exporté @limit_frame applique @soft_knee en parallèle sur une trame stéréo de 512×2 flottants via SIMD_MAP, convertit le résultat en vue d'octets sans copie (AS_BYTES) et calcule son empreinte SHA-256 via un nœud @sha256 résolu depuis VG-Mesh :

NODE @limit_frame [intent: "Limit a 512x2 stereo frame and digest it", export] {
  SIGNATURE: (frame: Tensor<f32, [512, 2]>) -> (Tensor<f32, [512, 2]>, Array<u8, 32>);
  EFFECTS: [];
  CONTRACT {
    PRE:  forall(i in 0..512, c in 0..2) { is_finite(frame[i, c]) };
    POST: forall(i in 0..512, c in 0..2) { result.0[i, c] >= -1.0 && result.0[i, c] <= 1.0
                                           && ((frame[i, c] >= 0.0) == (result.0[i, c] >= 0.0)) }
          && result.1 == spec:sha256(as_bytes(result.0));
    COST: heap_bytes == 0 && arena_bytes == 0;
    BUDGET: latency_p99_us <= 500;
  }
  LEARNABLE {
    knee: f32 in [0.5, 0.99];
  }
  BODY {
    %0 = SIMD_MAP(@soft_knee, frame, knee);
    %1 = AS_BYTES(%0);
    %2 = CALL_HASH(@sha256, %1);
    RETURN(%0, %2);
  }
}

La postcondition prouve mathématiquement que, pour toute trame stéréo finie possible et toute valeur de knee dans [0.5, 0.99], chacun des 1 024 échantillons sortants reste dans [-1, 1] en conservant son signe, avec zéro allocation sur le tas ou dans l'arène (heap_bytes == 0 && arena_bytes == 0), et que le condensat de 32 octets correspond exactement à la spécification spec:sha256.

7.7Vérifiez votre compréhension

Question 1

Quelle différence observe-t-on dans l'IR LLVM entre g01_add_bounded.vgs (vérifié) et b01_add_overflow.vgs --unverified ?

La preuve de non-débordement permet à vg-codegen de supprimer le contrôle dynamique et d'attacher nuw (et llvm.assume), ce qui est interdit sans preuve.

Question 2

Pourquoi l'entrée vérifiée vg_* appelle-t-elle vg_fp_enter() avant d'exécuter le nœud interne ?

Les hôtes audio activent souvent le mode flush-to-zero sur les registres MXCSR ou FPCR. En restaurant l'environnement IEEE par défaut puis celui de l'appelant, VeriGraph garantit l'identité bit à bit avec vg-interp.

Question 3

Que fait un binaire compilé avec un manifeste système s'il tente d'ouvrir un fichier non accordé après le démarrage ?

vg-rt ouvre d'abord les poignées déclarées depuis argv, puis applique le confinement avant d'exécuter le graphe racine (ADR 0011).

À retenir · Chapitre 7

vg-codegen efface les gardes prouvées, convertit les preuves en attributs LLVM sûrs, normalise NaN aux frontières et produit des binaires reproductibles sur trois cibles, confinés dès le lancement par vg-rt et validés à chaque appel externe par une entrée vérifiée.
